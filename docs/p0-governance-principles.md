# P0 治理原则（D0）

> 状态：v0.3 · **评审通过**（2026-08-17 第六轮复审；后续任何修订需重新评审）。v0.3 纳入第五轮修订（审计信封相位化自洽、append-only 与留存对齐）；v0.2 已内嵌第四轮修订（鉴权执行点、副作用分层、tenant 机制解耦、证据口径）。
> 范围声明：**只定原则，不定具体权限点与审计事件目录**——资源×动作权限矩阵、Run/模板/审批审计事件目录在 PRD 定稿后细化（依赖顺序见 aiops-platform-reuse-and-roadmap.md §3）。
> 上游：roadmap §3 P0 底座 A；§4 审批服务验收范围。

## 1. 角色模型原则

- 平台侧沿用现有 `owner | admin | member`；
- 运营侧新增角色按**职责 capability** 原则定义：申请人（发起 Run）、审批人（批准/驳回/要求修改）、审计员（只读回看）；
- 角色到权限点的具体映射属权限矩阵 spec（PRD 后），本文件只约束：**每个权限点必须可归因到至少一个职责 capability，否则该权限点不应存在**；
- 一个用户可持有多个角色，但**同一 Run 内申请人与审批人互斥**（见 §3 SoD）。

## 2. 默认拒绝（deny-by-default）与执行点

- 一切未显式授权的动作一律拒绝；
- **策略决策逻辑集中复用**（统一权限判断实现），但**鉴权在每个可信写入/执行边界执行**，包括：BFF、领域服务、审批回调、工作流 Worker、Tool Gateway——任何一条内部链路被直达调用（绕过 BFF）时，下一层边界必须仍能拒绝；
- 检查点失败（权限服务不可用）时同样拒绝，不降级放行（fail-closed）。

## 3. 职责分离（SoD）

- 申请人与审批人不得为同一用户（服务端硬约束；UI 提示不构成 SoD）；
- 转交/代理不改变 SoD 约束的判定主体；
- 附条件批准的条件执行校验不得由原申请人单方面完成（该能力本身不在 P1，见 PRD §10 裁决 3）。

## 4. Tenant Ownership 五原则

1. 每个聚合根具有明确 tenant ownership；
2. 子资源继承租户边界——**原则要求的是"不可绕过的继承"，机制可以是复合键、FK、tenant-scoped repository 或事务约束等价物**（仓库现行惯例为应用层约束而非数据库 FK，机制选型随各领域 schema 定，不在此强制）；
3. 所有查询与后台任务从可信上下文获得 tenant（禁止从客户端参数取 tenant 后不加校验地使用）；
4. 高风险表可冗余 tenant_id 强化查询与约束；
5. 隔离用真实跨租户负向测试证明，不以"字段存在"为验收。

## 5. 统一审计信封与副作用分层

**必填字段**缺失视为不合规、拒写入；**条件字段**按事件类校验：

| 字段 | 必填性 | 说明 |
|------|--------|------|
| actor | 必填 | 用户 / agent / 系统组件（含身份类型） |
| tenant | 必填 | 租户标识 |
| resource | 必填 | 类型 + id |
| resource_version | 条件 | **资源有版本时必填**（与版本快照对齐：审计必须能回答"批的是哪个版本"） |
| action | 必填 | 动作 |
| phase | 必填 | `intent` / `result` / `reconciliation`（三段审计相位） |
| result | 必填 | `pending` / `success` / `failure` / `uncertain`（intent 相位恒为 `pending`） |
| ts / trace_id | 必填 | 时间戳与追踪关联 |

**按事件类的强制扩展字段**：审批决策类事件必填 `plan_hash` 与 `evidence_snapshot_id`（与 PRD K2 对齐）。

- append-only：**常规业务操作不可改写、不可删除**；唯一例外是**受控生命周期操作**（到期清理、脱敏修正、tombstone），此类操作本身必须留审计记录（操作者、时间、依据策略）——与 §6 留存原则对齐。

**按副作用类型分层的写入一致性**（强一致不能 blanket 覆盖外部副作用）：

| 层 | 对象 | 一致性要求 | 相位映射 |
|----|------|------------|----------|
| 控制面 | 只写自有数据库的操作（审批决策、状态迁移、配置变更） | 审计与业务变更**同事务提交**（outbox 同库），审计未落则业务未落 | 单事件，phase=result |
| 外部副作用 | 调用外部系统的操作（工具执行、下游变更） | **intent → result 两段**：先落 intent（result=pending），再发起调用，后落 result（success/failure）；不允许只在成功后补记 | phase=intent → phase=result |
| 不确定态 | 结果不可确认（超时/网络中断/结果未知） | result 落 `uncertain`，阻止同键后续自动重试盲撞，进入对账流程；对账结论以 reconciliation 相位事件闭环 | phase=result(uncertain) → phase=reconciliation |

- **禁止**从"审计写入失败"推导"外部副作用已回滚"——外部调用无本地事务可回滚，只能走 result 缺失 → uncertain → 对账路径。

## 6. 脱敏与留存原则

- 凭据、密钥、PII 在审计与日志中默认脱敏；**脱敏发生在写入时**（写入原文、读取时过滤 = 不合规）；
- 留存分级（默认留存期、安全事件延长留存——具体天数待评审定标）；到期清理走 §5 受控生命周期操作，产出 tombstone 而非静默删除；
- 防篡改：append-only 为底线；哈希链/WORM 等强化机制按成本权衡列为开放问题。

## 7. 原则落地的验收方式

原则不是文档存在即落地，逐条对应负向测试：

| 原则 | 证明方式 |
|------|----------|
| 默认拒绝 | 未授权动作被拒的负向测试（在每个可信边界各至少一条，含绕过 BFF 直达服务层的调用） |
| SoD | 同用户申请+审批被拒的负向测试 |
| 租户隔离 | 真实跨租户访问（IDOR）负向测试 |
| 审计信封 | 必填字段缺失被拒写入、条件字段（resource_version）按事件类校验的测试 |
| 副作用相位闭环 | intent（result=pending）落库后才允许外呼、result/uncertain 必落、对账以 reconciliation 相位闭环的测试 |
| 受控清理 | 到期清理产出 tombstone、清理动作本身留审计、常规业务改删被拒的测试 |
| 写入时脱敏 | 审计存储中无明文敏感值的断言测试 |

**证据口径**：测试必须在规定的数据库/runtime 环境中实际执行通过，并保存**命令、结果与环境证据**（执行记录）；"测试文件存在"、mock 通过、或仅单一 SQLite 模式下的通过不构成验收证据。

## 8. 非目标

- 具体 RBAC 权限点矩阵（PRD 后）；
- 审计事件目录（Run/模板/审批事件清单，PRD 后）；
- 留存天数与防篡改机制选型（评审定标）；
- SSO 接入（可选准入工作流，按客户要求启动）。
